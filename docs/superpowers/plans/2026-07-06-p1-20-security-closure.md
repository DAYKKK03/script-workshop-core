# P1-20 安全收口与 Staging 可信基线恢复

更新时间：2026-07-06（Asia/Shanghai）

## 为什么这样设计

P1-20 不是在扩展业务能力，而是在先止血、恢复仓库可信基线。当前最直接的风险有两个：

1. 临时管理员初始化 API 一旦回到公开路由，会把高权限入口暴露到应用表面。
2. 本地部署文档和日志一旦保留真实凭据，即使没有服务器访问权，也会让仓库本身失去可信度。

因此本轮优先选择“删除暴露面 + 保留受控脚本 + 文档全部占位符化”，而不是继续给临时接口加更多条件判断。

## 方案内容

1. **管理员初始化只保留服务端脚本路径**
   - 仓库中不再保留 `app/api/bootstrap-admin/route.ts`。
   - 继续使用 `scripts/bootstrap-admin.ts` 与 `lib/admin/bootstrap.ts` 的一次性文件输出流程。
   - 好处：初始化材料只写到受限文件，不经 HTTP 返回，不进入浏览器和前端日志。

2. **文档与日志统一脱敏**
   - 所有本地部署说明只保留变量名、占位符和操作步骤。
   - 不再把数据库密码、Session Secret、MFA 加密密钥、Provider Key、EdgeOne 回源密钥写入仓库文件。
   - 好处：仓库可以继续作为运行手册存在，但不再携带可直接复用的秘密。

3. **用测试守住边界**
   - 安全测试断言：临时 `bootstrap-admin` 路由文件不存在。
   - 安全测试断言：目标文档和日志中不得出现真实凭据形态。
   - 好处：后续如果有人为了排障再次把临时接口或真实密钥写回仓库，测试会第一时间阻断。

## 这轮能做到什么

1. 从代码仓库层面移除临时管理员 HTTP 暴露面。
2. 把本地部署文档与工作日志恢复成“只留变量名、不留真实值”的可提交状态。
3. 在 `BUG_LOG` 和状态文档中留下明确的安全事件与后续轮换清单。

## 这轮做不到什么

1. 不能替代真实服务器和供应商侧的密钥轮换。
2. 不会自动修复已经流出到服务器、聊天记录、终端历史或第三方平台中的旧密钥。
3. 不处理真实抖音提取失败、EdgeOne 新配置或任何 UI 功能改动。

## 后续止损边界

1. 先完成密钥轮换，再继续任何真实 Provider 联调。
2. staging 如需再次创建管理员，只能走受控 bootstrap 脚本，禁止恢复 HTTP 临时接口。
3. 后续部署文档若需要分享给他人，只允许保留变量名清单和占位符。

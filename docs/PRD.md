# 短视频脚本拆写优化网站 PRD v1

## Summary

第一版做一个面向本地生活商家的抖音短视频脚本拆写工具。用户通过“账号 + 密码 + 邀请码”注册登录；登录后创建商家项目，用一个大文本框维护店铺资料；生成脚本时，用户选择商家项目，粘贴抖音视频链接，系统自动提取口播文案，按原文结构拆解参考脚本，最后用户选择时长，系统结合该商家项目的最新资料生成可直接复制的新口播脚本文案。

第一版只支持抖音链接自动提取，不做小红书、视频号；不做手动粘贴兜底；不做历史记录；不做站内编辑。

## Key Product Requirements

### 登录注册

- 注册必填：账号、密码、邀请码。
- 没有有效邀请码不能注册。
- 登录后进入工作台。
- 用户只能看到自己的商家项目。

### 商家项目

- 一个商家/店铺对应一个项目。
- 项目资料只用一个大文本框维护，不拆复杂字段。
- 用户可自主进入商家项目更新资料，系统不主动提醒更新。
- 如果用户更新了项目资料，后续生成脚本必须使用最新保存的项目资料。
- 资料建议写入：店铺名字、位置、主营内容、店铺特点、菜品/套餐/活动、菜品特色、当前活动、其他补充信息。

### 抖音口播提取

- 用户输入抖音视频链接。
- 系统必须通过安全、合规的提取能力自动获取口播脚本内容。
- 不做手动粘贴文案兜底。
- 如果链接无效、无法访问、无法提取口播内容，页面明确提示：`当前链接无法自动提取，请更换可提取的抖音视频链接`。
- 不允许用不稳定或违规的硬抓取方式作为核心实现。

### 参考脚本拆解

- 拆解必须基于自动提取出的原口播文案。
- 展示方式为“结构名称 + 对应原文”。
- 结构必须忠实匹配参考脚本，不能随便总结、不能脱离原文重编。
- 示例展示：
  - 开头共情钩子：原文片段
  - 场景/痛点引入：原文片段
  - 菜品/套餐/活动介绍：原文片段
  - 卖点/体验/信任强化：原文片段
  - 结尾行动引导：原文片段

### 新脚本生成流程

1. 用户选择商家项目。
2. 用户粘贴抖音视频链接，系统自动提取原口播文案。
3. 系统拆解参考脚本，输出“原文结构 + 原文片段”。
4. 用户选择脚本时长。
5. 系统根据参考结构和用户选择的商家项目最新资料生成完整口播文案。

### 新脚本生成要求

- 完整新脚本必须参考原脚本结构。
- 完整新脚本内容必须来自用户选择的商家项目资料。
- 不能继续沿用原商家的菜品、活动、店名、地址或卖点。
- 用户可以直接复制生成结果。
- 第一版不做站内编辑。

## 输出内容

- 自动提取的原口播文案。
- 参考脚本结构拆解。
- 完整新口播脚本文案。
- 复制按钮。
- 时长选项：15-30 秒、30-60 秒、60-90 秒。

## Assumptions

- 第一版只支持抖音链接自动提取。
- 第一版不支持用户手动粘贴口播文案。
- 第一版不支持小红书、视频号。
- 第一版不做历史记录、站内编辑、支付、会员、团队协作、批量生成。
- 项目资料更新由用户自主完成，系统不做更新提醒。
- AI 生成逻辑以“参考脚本结构”为骨架，以“所选商家项目最新资料”为内容来源。

## V2 实施中：爆款选题 + Top 3 优先拍

「爆款选题」已进入实施阶段，但尚未上线，不属于 PRD v1 已交付范围。设计事实来源为 `docs/TOPIC_IDEAS_DESIGN_SPEC.md`。

核心流程：

```text
选择商家项目
→ 读取项目最新资料
→ AI识别行业赛道
→ 推荐5个行业关键词和5个消费对象/消费场景
→ 用户确认或修改
→ 按5×5组合生成25个选题
→ 推荐引流、信任、转化各1条Top 3优先拍
```

每个选题包含标题、开篇、核心钩子、1—2种爆款元素和应用说明，不生成或展示脚本类型。爆款元素固定为：成本、借势、对立、幕后、反差、猎奇、人群、怀旧、糟糕、性感；高风险元素必须按安全规则改写，不得虚构、侵权、低俗、攻击群体或竞品。

Top 3 必须来自 25 宫格且互不重复，分别承担 `traffic`（引流）、`trust`（信任）、`conversion`（转化）目标，展示推荐理由、拍摄难度、素材、场景和风险提醒，不展示爆款概率、预计播放量或伪精确分数。

桌面端使用 5×5 宫格，移动端按 5 个消费对象/场景分组展示。本期不保存历史或反馈、不批量导出、不直接生成完整脚本、不接入实时热点，也不承诺生成结果一定成为爆款。默认每账号每日成功生成 5 次，后台可按账号调整；分析不扣额度，完整返回25条及Top 3后才扣1次。

## V2 staging 验收前：定制化脚本

「定制化脚本」用于用户已经明确想拍什么、或已从爆款选题得到方向时，直接生成一条可复制的完整口播。设计事实来源为 `docs/CUSTOM_SCRIPT_DESIGN_SPEC.md`，写作事实来源为 `docs/CUSTOM_SCRIPT_WRITING_RULES.md`；当前已完成本地阶段 3 实现，但不属于 PRD v1 已交付范围，staging migration、真实 DeepSeek、事实边界与页面验收通过前不得推生产。

核心流程：

```text
选择商家项目
→ 输入自由创作要求或粘贴爆款选题方案
→ 确认引流/信任/转化目标和表达风格
→ 服务端读取商家最新资料
→ 生成一条完整口播（创作目标约200—350字）
→ 复制或换一版
```

产品要求：

- 页面为登录保护的 `/custom-scripts`，没有商家项目时引导用户先创建项目。
- 输入兼容自由需求、普通爆款选题和 Top 3；Top 3 可自动继承目标，但用户可以修改。
- 创作要求输入框不设置浏览器原生 `maxlength`；前端完整接收键入或粘贴内容，再按共享 NFC + Unicode code points 规则显示和校验。超过 5000 时不静默截断，必须保留输入、显示错误并禁用提交。
- 爆款选题复制文本使用固定五行头：从首个非空行开始依次为标识行、`sourceProjectId`、`sourceType(topic|top_pick)`、`sourceObjective(auto|traffic|trust|conversion)`、商家项目展示名，选题正文从第六行开始（即该头之后的第一行）；头前只允许由 Unicode `White_Space` 或 FEFF 组成的空白行。复制项目名时将 CR、LF、U+2028、U+2029 替换为空格，再将连续 Unicode whitespace 收敛为单个空格并 trim；项目名不参与安全判断。服务端必须从原文本解析官方头，与对应来源字段逐项核对，并确认来源项目属于当前用户且等于所选 `projectId`。官方标识或任一保留机器字段出现在正确五行头之外（包括前置空白区）时阻止生成；只有全文完全没有官方标识及三个保留机器字段的旧版/外部文本，才提示以当前项目为准。Top 3来源目标只认 `sourceObjective`，不猜中文标签；首次识别或切换来源时，普通选题重置为 `auto`、Top 3继承其明确目标，用户随后仍可修改实际 `objective`，服务端不得要求二者相等。
- 结果只包含自然口播正文和实际字数，保留模型的自然段落与换行，不包含标题、分镜、时间轴、结构分析或 AI 推理。
- 文本统一经 NFC、CRLF/CR→LF 和边界 trim 规范化；边界 trim 去除 FEFF。正文只移除 Unicode `White_Space` 后按 Unicode code points 计数，内部 FEFF 不移除并计1，中文、英文、数字、标点各计1。页面创作目标约200—350字，Prompt 目标为240—300；服务端内部安全范围为80—350（含边界），80—199的完整安全口播可直接成功，不向用户或Prompt暴露80底线。段落、换行、单句长度和句末标点不作为硬门槛，服务端不得自动拆句；正文整体必须至少包含一个 Unicode 字母或数字。前后端统一复用 `lib/custom-scripts/text.ts`。
- 商家最新 `profileText` 是唯一商业事实来源。用户要求和粘贴选题只决定创作方向，不能引入商家资料外的价格、活动、地址、工艺、数据、资质、功效、服务动作或效果承诺。
- 默认不添加行动引导；只有转化目标或用户明确要求时，允许一个自然轻引导。
- 资料缺失但可删除无依据内容继续创作时继续生成；缺失内容决定主题时返回1—5个固定缺失资料码，不生成半成品。固定码与唯一中文映射共18项：`main_product`→主营产品、`core_selling_point`→核心卖点、`target_audience`→目标人群、`consumption_scene`→消费场景、`price`→价格、`promotion`→活动、`address_or_service_area`→地址或服务区域、`service_process`→服务流程、`qualification`→资质、`proof_or_case`→证据或案例、`effect_claim`→效果依据、`production_process`→生产或制作流程、`materials_or_ingredients`→材料、原料或成分、`service_action`→服务动作、`business_hours`→营业时间、`contact_method`→联系方式、`business_data`→经营数据、`warranty_or_after_sales`→质保或售后。模型只返回 code；前端只做本地中文映射，服务端白名单校验且不展示 AI 自由文本。
- 固定使用 `CustomScriptGenerationJob` 与独立 Worker，任务创建起120秒 run deadline，终态最多保留30分钟；输入在终态立即清空、商家正文不入任务、不提供历史列表。页面 mount 时通过 `/api/scripts/generate-custom/current` 恢复当前用户最新且未过期的单个 `queued|processing|succeeded|needs_profile|failed|canceled` 任务。
- 使用 `deepseek-v4-flash` 非思考模式。每次 Provider 请求固定 `maxAttempts=1` 且禁用 envelope retry；语义最多尝试2次并共享120秒任务截止，总 Provider 调用不超过2次。
- 同用户同 `clientRequestId` 唯一并保存 `inputHash`：各文本依次执行 NFC、CRLF/CR→LF、trim，枚举不变；固定数组 `[projectId,requestText,objective,tone,previousScript||'',sourceProjectId||'',sourceType||'',sourceObjective||'']` 经 `JSON.stringify` 后取 SHA-256，`clientRequestId` 不参与。同 UUID 同 payload 返回原任务，不同 payload 返回幂等冲突；同用户最多一个活动任务。
- 定制化脚本独立每用户每小时最多创建10个新任务，`needs_profile` 和失败也计小时限制；共用现有每日脚本额度，每次首次生成或换一版仅在成功后扣一次。
- POST 创建任务前先调用 `assertDailyScriptQuota` 执行每日脚本额度快速检查；成功结果、`quotaChargedAt` 与上海时区当日脚本使用量在同一个 Serializable 事务再次检查并提交；失败、超时、取消和资料不足不扣每日额度。
- Job 持久化 `providerCallsStarted` 和 `semanticAttempt`。Provider 调用前仅在 Worker 仍持有 processing 锁且未过截止时间时原子递增，最多2次；锁30秒失效且每10秒心跳，重领任务必须沿用剩余次数，失锁 Worker 不得写终态、结果或额度。
- 生成中提供“取消生成”；仅允许取消尚未扣额的 `queued|processing` 任务，取消与完成通过条件更新竞争且只有一个终态获胜，取消成功立即清空输入、结果和锁。
- 商家资料、用户需求和 Prompt 使用安全 JSON 序列化传入模型，不拼接可被输入闭合的 XML/伪标签。
- 页面明确提示：`结果仅临时保留30分钟且不进入历史，请及时复制。`
- 定制脚本全部成功 API 使用 `{ success: true, data: ... }` 包装；页面恢复、轮询和取消共用同一任务快照契约。
- 不保存历史、不站内编辑、不批量生成、不做模板库、不承诺播放或转化效果。

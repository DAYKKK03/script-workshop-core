## Long-lived Context

- 2026-08-23 staging deploy no longer creates a shared-queue ExtractionJob as a release blocker. It retains Web/database health and exactly-one-worker checks, then requires a sanitized `douyin_extraction_worker_tick` from the exact newly started worker container, filtered from that container's own start time and rechecked against the same start identity. Missing, stale, or restarted-container ticks fail closed with an existing fixed category and use normal rollback; no raw container log is emitted. This proves only startup/first scan, not business queue throughput, retention, or Provider capability. The isolated PostgreSQL `worker-functional.test.ts` remains the separate claim-to-`EXTRACTION_SOURCE_EXPIRED` behavior proof.



- Douyin extraction must stay behind a compliant provider boundary. No manual paste fallback, upload fallback, scraping bypass, or mock success.
- The current staging extraction path is `TikHub -> optional Volcengine ASR -> DeepSeek`, with fixed user-facing extraction failure copy.
- The Volcengine voice staging probe stays network-free by default. A live attempt requires all explicit staging gates plus a server-only durable one-time authorization record that is atomically consumed before transport. Its parent must be a prebuilt, real-path, runtime-owned `0700` directory (no symlinks); the marker must remain a runtime-owned, regular `0600` file with an inode check. Any unsafe filesystem state fails closed with the sanitized gate code. Runtime clone/status/synthesis/private-storage boundaries share one deadline and AbortSignal, with a timeout race for non-cooperating adapters.
- The Volcengine voice runtime additionally fences late effects: the READY repository update receives an absolute deadline and must enforce it atomically. Generated-MP3 cleanup now persists its token-scoped state in PostgreSQL before PUT; `WRITING` is never completed merely because an object is absent, matching-token settlement becomes `WRITTEN` or late `CLEANUP_READY`, and only a leased consumer with confirmed deletion may mark `SUCCEEDED`. A crashed, unsettled writer remains retryable pending settlement or an approved staging-key lifecycle reconciliation; this prevents false success but does not promise immediate object absence. It never returns an opaque audio reference until deadline-fenced publication. Runtime and V3 request construction reuse the shared text validation boundary; V3 parser line/total input limits and strict base64-length preflight run before audio allocation. V1 only accepts ready `2/4` and confirmed pending `1`; unknown states fail closed.
